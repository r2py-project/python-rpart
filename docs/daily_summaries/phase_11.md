### 1. Abstract

This session executed the `/convert-r-tests-to-python` skill to translate the complete R test suite at `rpart/tests/` (13 `.R` files) into pytest modules under `r2py_rpart/tests/`, using the `convert-r-test-to-python` subagent invoked sequentially, once per file, in the `r-to-python` conda environment. Each conversion was treated as a live correctness probe against the `r2py_rpart` port rather than a mechanical syntax translation: six of the thirteen conversions surfaced genuine, previously undetected bugs in the Python library (spanning survival-response marshaling, formula parsing, parameter flattening, C-buffer sizing, NA-row handling, categorical prediction, print formatting, and cross-validation), all of which were root-caused, fixed, and verified against live R reference runs before the corresponding test was finalized. The session concluded with all 13 R test files converted (zero failures, zero skips), a Python test suite grown from 12 to 38 passing tests, six new CSV data fixtures exported from R, and one documented, unresolved numerical discrepancy in cross-validated error trailing rows flagged for future investigation.

### 2. Methodology & Actions Taken

#### 2.1 Skill invocation and file discovery

The user invoked `/convert-r-tests-to-python` with arguments `rpart/tests/` (R source), `rpart/` (R library), `r2py_rpart/` (Python package root), `r2py_rpart/tests/` (Python test output directory), specifying that all execution/validation occur in the `r-to-python` conda environment. A recursive `find` over `rpart/tests/` identified 13 R test files: `backticks.R`, `cost.R`, `cptest.R`, `minus_in_formula.R`, `priors.R`, `rescale.R`, `testall.R`, `treble.R`, `treble2.R`, `treble3.R`, `treble4.R`, `usersplits.R`, `xpred1.R`, `xpred2.R`. The pre-existing Python test directory contained only `test_rpart.py` (12 tests).

#### 2.2 Sequential per-file conversion via subagent

Per the skill's instructions, each R file was converted by a dedicated `convert-r-test-to-python` agent invocation, run one at a time (not in parallel) to avoid fixture/library race conditions and to let each conversion build on bug fixes and fixtures established by prior ones. Each agent prompt explicitly listed: the R test path, the R library path, the Python package root, the output test directory, the conda environment constraint, the set of already-completed conversions and their fixtures (to avoid duplication or accidental overwrite), and the running list of library bug fixes already applied (to prevent regressions or accidental reversion). For the two largest/most novel files (`testall.R`, `usersplits.R`, `xpred2.R`), the prompts additionally supplied targeted technical context — e.g., pointers to the relevant R source functions, hints about likely `yval2`/`splits` column semantics, and explicit instructions to read specific Python source files (`xpred_rpart.py`, `predict_rpart.py`, `rpart.py` line ~316 for the `method=4` user-callback dispatch) rather than guess at APIs.

The first invocation (`backticks.R`) exhibited anomalous behavior: the async agent appeared to spawn and wait on its own nested background sub-agent, producing several duplicate/delayed `task-notification` events before a final, correct result was confirmed. This was resolved by sending a follow-up message asking the agent to report its final status directly; subsequent invocations were instructed explicitly to "do this work directly yourself rather than spawning further nested agents," which eliminated the recurrence for all 12 remaining files.

#### 2.3 Environment integrity issue and remediation

During the `priors.R` conversion (5th file), the agent discovered that the `r-to-python` conda environment held a **stale, non-editable installation** of `r2py_rpart` in site-packages — one that predated even the `.T`-transpose and `. - column` formula-parser fixes made earlier in this same session (i.e., the installed package did not reflect current repo source at all). #### 2.4 Per-file conversion details

1. **`backticks.R` → `test_backticks.py`.** Tests that R's backtick-quoted formula identifiers (for column names containing spaces) are handled by `r2py_rpart`. Traced the mechanism to `_strip_backtick()` in `model_frame_rpart.py`, which already mirrors R's own `sub("^\`(.*)\`$","\\1",...)` term-cleanup regex — no library change needed. Used `sklearn.datasets.load_iris()` reconstructed with R's canonical `iris` column names/species labels (verified row-for-row identical to R's built-in `iris` via `rpy2`) rather than requiring an R round-trip at test time. Added a second test case proving the space-containing name also works without backticks, isolating that Python's parser doesn't require backtick syntax. Result: 14/14 passing.

2. **`cost.R` → `test_cost.py`.** Exercises `Surv(time, status) ~ ...` cost-weighted classification splitting on the `survival::lung` dataset (228 rows), exported once as `tests/data/lung.csv` (verified per-column NA counts against R: `meal.cal` 47, `wt.loss` 14, `pat.karno` 3, `ph.ecog` 1, `ph.karno` 1). Since `r2py_rpart`'s formula parser does not parse `Surv()` syntax, the model frame was built by hand and tagged with a `_surv=True` attribute mirroring R's `inherits(Y,"Surv")` dispatch. **Bug found:** `rpart.py`'s `ymat` construction used `Y.T.ravel()` where R's `as.double(t(init$y))` (column-major transpose-then-flatten) is mathematically equivalent to a plain row-major `Y.ravel()` — the erroneous `.T` silently scrambled the `[time, status]` per-observation pairing for any multi-column (`ny>1`) response, invisible to all prior single-column-response tests. Fixed by removing the `.T`. Result: 15/15 passing.

3. **`cptest.R` → `test_cptest.py`.** Verifies that rpart's `cp` scales correctly with dataset size (50-row `mystate` vs. a 1000-row 20x replicate, `minsplit`/`minbucket` scaled 20x). Exported `tests/data/mystate.csv` (R's `state.x77` + `state.region`, reused by five later files). No library bug found. Result: 16/16 passing.

4. **`minus_in_formula.R` → `test_minus_in_formula.py`.** Tests formula syntax `mpg ~ . - gear` and `mpg ~ . - gear - carb` (the feature request from upstream rpart issue #7) on `mtcars` (exported as `tests/data/mtcars.csv`). **Bug found:** `model_frame_rpart.py::_parse_formula_terms` only supported bare `"y ~ ."` or plain `"y ~ x1 + x2"` term lists; a right-hand side combining `.` with `-` exclusions was treated as one malformed literal term, raising `KeyError`. Fixed by adding a `_tokenize_rhs` top-level `+`/`-` tokenizer and reworking `_parse_formula_terms` so `.` expands to all remaining columns and `- name` removes a column from the accumulated term list, mirroring R's formula algebra. Verified against a live `Rscript` run. Result: 18/18 passing.

5. **`priors.R` → `test_priors.py`.** A numeric "hard-core" test of Gini splitting under a non-uniform `prior=c(.5,.3,.2)`-style vector and a non-symmetric 3×3 `loss` matrix on a synthetic 15-row dataset with missing values, checking exact deviance/`yval2`/split-improvement values re-derived analytically. **Bug found:** `rpart.py` flattened every value in `init["parms"]` (the dict holding `prior`/`loss`/`split`) via a plain row-major `.ravel()`; R's `unlist()` on a list containing a matrix yields the matrix's native **column-major** storage order, so a genuinely 2-D, non-symmetric `loss` matrix was silently transposed in the flattened byte layout passed to `giniinit()` in `rpart/src/gini.c`. This corrupted the root node's predicted class (came out as class 3 instead of R's correct class 2). Fixed by raveling `ndim>=2` parms values (e.g., `loss`) with `order='F'` and 1-D values (e.g., `prior`) with ordinary order. Also surfaced and fixed the stale-install environment issue described in §2.3. Result: 19/19 passing.

6. **`rescale.R` → `test_rescale.py`.** Tests `rpart_exp` (the Poisson/exponential response-rescaling function) directly against a hand-computed cumulative-hazard table for a 9-observation `Surv` response over four inter-death intervals. Mapped R's `approx(x,y,xout)$y` to `numpy.interp(xout,x,y)` (reversed argument order) and `all.equal` to `numpy.allclose`. No library bug found; no new fixture needed (inline data). Result: 20/20 passing.

7. **`testall.R` → `test_testall.py`.** The largest and most heterogeneous R test file — an informal, printout-driven script (rather than `testthat`-style) exercising Poisson survival splitting (`stagec`), continuous-anova splitting with `xpred.rpart` cross-validation (`mystate`/`state.x77`), two classification variants with differing priors (`stagec`), and an ordered-factor-response classification model (`cu.summary`, "car reliability" data). Split into six pytest functions, one per original model fit (`test_fit1_poisson_survival_stagec`, `test_fit2_default_method_is_exp_survival_stagec`, `test_fit4_continuous_anova_mystate_and_xpred`, `test_fit5_simple_classification_stagec`, `test_fit6_classification_with_equal_priors_stagec`, `test_carfit_ordered_factor_response_cu_summary`). Exported two new fixtures: `tests/data/stagec.csv` and `tests/data/cu_summary.csv`. All three of the R script's genuine `all.equal()` assertions were preserved as exact `np.allclose` checks (passing to full floating-point precision); autoprint-only calls (bare `fit1`, `summary(fit5)`) were converted to structural well-formedness assertions plus numeric spot-checks against a live R reference run. **Seven real bugs found and fixed**, none previously caught by the prior six conversions:
   - `rpart.py` / `xpred_rpart.py`: `float(controls["xval"])` crashed whenever `xval` was an explicit fold-assignment array rather than a scalar fold count; fixed by flattening `controls["xval"]` into the tail of the `opt` array instead of assuming a scalar.
   - `__init__.py`: `dsplit`/`isplit`/`csplit` C output buffers were sized `n*3`/`n*nvar`, undersized whenever `maxcompete+1+maxsurrogate` is non-trivial relative to `n`; corrected to the true worst-case bound `(n-1)*(maxcompete+1+maxsurrogate)`.
   - `model_frame_rpart.py`: `m.attrs['response']` was cached **before** `na_rpart()` dropped missing-data rows, leaving it silently length-mismatched with the filtered frame — fatal for `carfit` (32 of 117 `cu.summary` rows dropped). Fixed by re-deriving the response after NA-filtering.
   - `predict_rpart.py` / `pred_rpart.py`: `predict(newdata=...)` with categorical columns crashed because `newdata` was never re-encoded via the fit's stored `xlevels` (mirroring R's `model.frame.rpart`-based re-encoding), and `pred_rpart` assumed a plain DataFrame rather than the `RpartMatrix` object `rpart_matrix()` actually returns. Both fixed.
   - `print_rpart.py`: the non-classification `_signif()` fallback called `numpy.round(arr, decimals_array)` with a per-element decimals array, which NumPy rejects — broke `print()` for every anova/poisson/exp tree; fixed via element-by-element rounding at two call sites.
   - `print_rpart.py` / `summary_rpart.py` / `printcp.py`: all three reported the "N observations deleted" count as `len(na_action)` (a fixed-size, 3-key dict — always reporting "3") instead of `len(na_action['indices'])`; fixed in all three files.
   - `labels_rpart.py`: categorical split labeling crashed with multiple categorical predictors of differing level counts (`Country`, 10 levels; `Type`, 6 levels), because `csplit` rows are padded to the dataset-wide `maxcat` and NumPy boolean indexing (unlike R's permissive out-of-range recycling) requires exact-length masks; fixed by truncating each `csplit` row to the variable's true level count before indexing.

   One **unresolved, documented discrepancy** remains: the trailing 1–3 rows of `xerror`/`xstd` in `fit1` (`cp=0`) and `fit6`'s cptables show a small, fully reproducible divergence from R that was investigated at length — ruled out as caused by any of the seven fixes above, and ruled out as memory-nondeterminism — but not fully root-caused, since the underlying `rpart.c`/`xval.c` C sources are byte-identical to R's. The test asserts exact precision on all unaffected rows/quantities and a documented sanity bound on the few affected trailing values. Result: 26/26 passing.

8. **`treble.R` → `test_treble.py`.** First of four "trebled weights" tests: verifies that tripling all case weights on a Poisson/survival fit (`stagec`, unshrunk `parms=list(shrink=0)`) scales `frame$wt`/`frame$dev`/`yval2`/`splits$improve`/`variable.importance` by exactly 3×, and separately that replicating rows by an integer weight vector produces (nearly) the same fit as using `weights=` directly, with two explicitly R-documented exception rows (R 1-indexed rows 49/64 → Python 0-indexed 48/63, corresponding to a surrogate-split tie broken differently by row-replication vs. weighting). Reused the `stagec.csv` fixture from `testall.R`. Since this test requires the hand-built `Surv` model frame path, weights were attached via `m.attrs["weights"]` (confirmed by reading `rpart.py`'s `wt = m.attrs.get("weights")` extraction). No library bug found. Result: 28/28 passing.

9. **`treble2.R` → `test_treble2.py`.** The regression/anova analogue of `treble.R`, using the formula-string + `data=` + `weights=` path (not the hand-built-frame path) on `mystate` (reusing `mystate.csv`). Three sub-tests: (a) weight=3 scaling of `frame$wt`/`frame$dev` and `sqrt(3)` scaling of `cptable`'s `xstd` column; (b) an inline 10-row dummy dataset with exact `frame$dev` value checks for weight 1 vs. 2; (c) a replicated-rows-vs-`weights=` comparison with `maxcompete=3, maxdepth=3` to sidestep a documented near-tie between the `life` and `murder` predictors. Correctly distinguished R's `rep(1:10,5)` (tile semantics, `numpy.tile`) from `rep(vector,length.out=n)` (resize semantics, `numpy.resize`) — verified against a live R session. No library bug found. Result: 31/31 passing.

10. **`treble3.R` → `test_treble3.py`.** The classification-tree analogue, on `cu.summary` (`Country ~ Reliability + Price + Mileage + Type`, `method='class'`; reused `cu_summary.csv`). Required careful translation of R's positional column indices: `frame[,5:7]` → `["yval","complexity","ncompete"]`; `yval2[,12:21]` (1-based) → Python `yval2[:,11:21]`, the 10 `yprob` columns for a 10-class response; the "surrogate?" check on `splits[,5]` → the `adj` column (0-indexed 4), where `adj>0` marks a surrogate split whose `improve` is left unscaled. No library bug found. Result: 32/32 passing.

11. **`treble4.R` → `test_treble4.py`.** The 2-class classification analogue, on the `kyphosis` dataset (part of the R `rpart` package itself, not base R or survival), newly exported as `tests/data/kyphosis.csv`. Uses `parms=list(prior=c(.7,.3), loss=matrix(c(0,1,2,0),nrow=2,ncol=2))` — care was taken to translate R's column-major matrix fill (`matrix(c(0,1,2,0),2,2)` = `[[0,2],[1,0]]`, not a row-major reading of the flat vector) correctly. Verified `yval2` has 6 columns for this 2-class response (`yval`, 2 counts, 2 yprobs, `nodeprob`), so R's `yval2[,2:3]` maps to Python's `[:,1:3]`. No library bug found. Result: 34/34 passing.

12. **`usersplits.R` → `test_usersplits.py`.** Exercises rpart's user-defined split-method feature (R's `method=list(eval=,split=,init=)`, reimplementing the anova rule from scratch in R closures `temp1`/`temp2`/`temp3`) and checks the resulting fit is identical to `method='anova'`. Verified callback signatures/return shapes directly against `rpartcallback.py` (`eval1`/`eval2`) and `rpart.py`'s `isinstance(method, dict)` dispatch branch (~line 316) before translating. Also cross-checked `xpred_rpart` between the user method and built-in anova method, and hand-reproduced `xerror`/`xstd` from a third fit exactly as the R script does. **Bug found:** `xpred_rpart.py`'s parms-flattening code handled only `dict` and `None` values, falling back to `list(parms)` for anything else — raising `TypeError: 'int' object is not iterable` whenever a user-defined `init()` returns a bare scalar `parms` (e.g., `temp3`'s `parms=0`, matching the built-in anova method's own convention). Fixed by mirroring `rpart.py`'s existing three-way `None`/`dict`/scalar-or-array branch using `np.asarray(parms).ravel()`. Reused `mystate.csv`. Result: 36/36 passing.

13. **`xpred1.R` → `test_xpred1.py`.** Tests `xpred.rpart`'s `return.all=TRUE` argument on a tiny inline 12-row dataset by manually reimplementing the expected output: looping over 3 xval-groups, refitting on each held-out-group-excluded subset, rescaling the refit's CP list to the subset's absolute-risk scale, pruning at each rescaled CP, and predicting on the held-out fold with `type='matrix'`. Confirmed `xpred_rpart`, `prune`, and `predict_rpart` in `r2py_rpart` already fully supported `return_all`, `prune(tree, cp=...)`, and `type='matrix'` respectively — no library bug found (this is an anova/`numresp==1` case, where `return_all` has no shape effect). Result: 37/37 passing.

14. **`xpred2.R` → `test_xpred2.py`.** The survival/Poisson-method analogue of `xpred1.R`, using `stagec` (`method='poisson'`, `numresp=2`) — deliberately chosen by the original R test authors for its mix of continuous, categorical, and missing values. This exercised the `numresp>1` branch of `xpred_rpart`'s `return_all=True` path, untested by any prior file in this batch. Verified the expected 3-D output shape `(146, 7, 2)` (observations × CP values × 2 response columns) by reading `predict_rpart.py`'s `type='matrix'` output shape for Poisson trees. **Bug found:** `xpred_rpart.py` contained the *same class* of row/column-major flattening bug originally fixed in `rpart.py` for `cost.R` (item 2 above), but in the separate cross-validation code path: `np.ascontiguousarray(Y.T, dtype=np.float64).ravel()` performs a C-order ravel of `Y.T`, equivalent to a column-major ravel of `Y`, scrambling the per-observation `[time,status]` pairing required contiguous by `xpred.c`'s `rp.ydata[i]` indexing. This silently produced degenerate, non-cross-validated (root-node-constant) output for any multi-column-response method — invisible to `xpred1.R`'s anova-only (`numy==1`) test, where transpose-then-ravel and plain ravel coincide. Fixed to a plain `np.ascontiguousarray(Y, dtype=np.float64).ravel()`. Verified against a live R rerun to displayed precision. Result: 38/38 passing.

### 5. Addendum (same-day follow-up, 2026-07-01): Root-Cause Investigation of the `xerror`/`xstd` Cross-Validation Discrepancy

This addendum documents a follow-up, forensic-level investigation into item (1) of the "Conclusion & Next Steps" above — the trailing-row `xerror`/`xstd` divergence in `fit1` and `fit6`'s cptables in `test_testall.py`, which §2.4 item 7 and the module docstring's "A remaining unexplained numerical discrepancy" section had flagged as investigated-but-unresolved. The goal was to push the investigation further: confirm or rule out each previously-considered hypothesis with direct, reproducible evidence rather than informed judgment, and, where possible, isolate the actual mechanism. All work below was exploratory/read-only with respect to the shipped package: every experimental patch (debug instrumentation, build-flag overrides, a scratch local R build) was reverted before the session ended, and `pytest tests/ -q` was re-confirmed green (38/38) afterward. No production code or test file was modified as part of this addendum.

#### 5.1 Live reproduction harness

Both a live R session and a live Python session were used side by side, in the same `r-to-python` conda environment already used throughout Phase 11 (confirmed `library(rpart)` resolves to version `4.1.27`, matching `rpart/DESCRIPTION`'s `Version: 4.1.27` exactly — i.e., not merely "the same rpart" but the same release the local `rpart/` source tree corresponds to). `fit1`'s and `fit6`'s cptables were reproduced from scratch with `options(digits=10)` on the R side and `pandas`'s float-format option set to 10 decimal places on the Python side, confirming byte-for-byte the exact numbers already recorded in the module docstring and in the `expected_xerror_precise` arrays in `test_testall.py`:

- `fit1` (poisson, `usesurrogate=0`, `cp=0`, 9 cptable rows): rows 1–6 (nsplit 0,1,3,4,5,6) match R to the full 10 digits printed; rows 7–9 (nsplit 7,8,9) diverge — R gives `0.9920323780, 0.9852934906, 1.0077320000`, Python gives `0.9861181333, 0.9793792459, 1.0018354158`.
- `fit2` (exp/survival, default control, `cp=0.01`, 8 cptable rows) was additionally re-checked at full precision (not just the loose `atol=5e-3` bound already in the test) as a control case: **every single row matches R exactly to 10 digits**, including the deepest row (nsplit=8). This is an important new data point — it shows the discrepancy is not simply "the last row of any sufficiently deep cptable is untrustworthy."
- `fit6` (classification, default control except `parms=list(prior=c(.5,.5))`, 6 cptable rows): rows 1–5 match R exactly; only row 6 (nsplit=9, the deepest) diverges — R gives `xerror=0.8639291465`, Python gives `0.8933172303` (also newly confirmed at full precision here, superseding the previously-recorded `0.8639` vs `0.8933` 4-digit comparison in the test file's comment with an exact 10-digit figure).

- The differences for fit1's three bad rows are themselves nearly a constant offset (`0.0059142447`, `0.0059142447`, `0.0058965842` respectively) rather than random-looking noise, which was the first hint that a specific, localized mechanism (not diffuse rounding) was responsible.

#### 5.2 Ruling out data precision loss in the CSV fixture

Hypothesis: `stagec.csv` (written once via R's `write.csv` per §2.4 item 7, then read back by `pandas.read_csv` in `test_testall.py`'s `_load_stagec()`) might have lost precision in continuous columns (`age`, `g2`, `gleason`, `grade`, `eet`, `pgtime`, `pgstat`) relative to R's live in-memory `data(stagec)`, and that this loss might not affect early/well-separated splits but could tip a close split later, only in deep nodes.

Test: an R script loaded both R's live `data(stagec)` and the checked-in `stagec.csv`, and computed `max(abs(orig - reload))` per numeric column plus an explicit search for any row where `orig != reload`, printing mismatches at 20 significant digits.

Result: **zero differences in every column** — the CSV round-trip is bit-exact. This hypothesis is ruled out.

#### 5.3 Ruling out C-source divergence between the two packages

Hypothesis, revisited more rigorously than the "byte-identical" characterization already recorded in §2.4 item 7 and the module docstring: perhaps some *other* C file besides `rpart.c`/`xval.c` (the two explicitly checked previously) differs.

Test: `diff -q` was run pairwise between `rpart/src/xval.c` vs `r2py_rpart/src/xval.c`, `rpart/src/rpart.c` vs `r2py_rpart/src/rpart.c`, and `rpart/src/mysort.c` vs `r2py_rpart/src/mysort.c` (the file responsible for the "sort indices, once and for all" step feeding cross-validation's `savesort`).

Result: **all three `diff -q` invocations produced no output** — confirmed byte-identical, reconfirming and extending the earlier finding.

#### 5.4 Ruling out compiler/optimization/architecture-flag divergence (new hypothesis, fully tested)

This is a genuinely new hypothesis not considered in the original Phase 11 session. The two packages are **not built the same way**:

- R's C compiler invocation (`R CMD config CC` / `CFLAGS`): `x86_64-conda-linux-gnu-cc -march=nocona -mtune=haswell -ftree-vectorize -fPIC -fstack-protector-strong -fno-plt -O2 -ffunction-sections -pipe ...` — plain C, `-O2`.
- `r2py_rpart`'s actual build command, extracted from `r2py_rpart/build/cp314/compile_commands.json`: `cc ... -O3 -fPIC -x c++ -std=c++14 -fkeep-inline-functions -fPIC ...` (meson's default release `buildtype` implies `-O3`; `r2py_rpart/meson.build`'s `c_args` forces every `.c` file to be compiled *as C++* via `-x c++ -std=c++14`, with no explicit `-march`/`-mtune`, so it floats on the toolchain's default `-march=x86-64-v2`).

Given the C sources are byte-identical (§5.3) but the *compilation strategy* is not (different language mode, different optimization level, different target ISA baseline), it is entirely plausible that identical floating-point source expressions produce different machine code — e.g. via FMA (fused multiply-add) instruction-contraction differences between GCC's C and C++ front ends, or via `-O3`'s more aggressive vectorization/inlining relative to `-O2`.

Two escalating tests were run:

1. **Isolated FMA-contraction test.** A minimal `double f(double a,double b,double c){return a*b+c;}` was compiled four ways: with R's exact real flags, with Python's exact real flags (both taken verbatim from the commands above), and with each toolchain's respective defaults. In **every** combination the generated assembly was `mulsd` immediately followed by `addsd` — i.e. **no FMA contraction occurs in either build**, because `-march=nocona` (R) and the toolchain's default `-march=x86-64-v2` (Python) both predate/exclude the FMA3 instruction set entirely, so GCC cannot emit a fused instruction regardless of language mode or optimization level. This rules out FMA contraction specifically.
2. **Direct, decisive experiment: rebuild the real extension with R's real flags.** `r2py_rpart/meson.build`'s `c_args` list was temporarily edited to append `'-O2', '-march=nocona', '-mtune=haswell'` (later flags win on a GCC command line, so this makes the *actual* `_rpart_core.so` build use R's exact optimization level and target architecture, while still necessarily compiling as C++ per `-x c++ -std=c++14`, since the fake R headers require C++ features). The extension was rebuilt via `pip install --no-build-isolation .` in the `r-to-python` env, and `fit1`'s cptable was recomputed.

Result: **the discrepancy was completely unchanged** — Python still produced `0.9861181333, 0.9793792459, 1.0018354158` for rows 7–9, identical to the un-patched build. This **conclusively rules out compiler optimization level, target architecture flags, and (independently, per test 1) FMA contraction** as the cause. The `meson.build` edit was reverted afterward (confirmed via `git checkout --` and a clean re-`pip install`); no trace of this experiment remains in the repository.

#### 5.5 Confirming the deterministic full tree is exact to the deepest leaf

Before assuming the bug is confined to cross-validation, the *non-cross-validated* structure of `fit1`'s full tree was compared node-by-node against R's printed tree in `rpart/tests/testall.Rout.save` (already quoted in `test_testall.py`'s own comments, but not previously verified field-by-field beyond `n=146` and the root variable). Python's `fit1["frame"][["var","n","dev","yval"]]` was printed and diffed by eye against R's `node), split, n, deviance, yval` printout.

Result: **every single node matches** — same split variable, same `n`, same `dev`, same `yval`, at every depth down to every terminal leaf (including the smallest leaves, e.g. node 9 with `n=7`, node 104 with `n=7`). This confirms the bug is 100% confined to the cross-validation refit loop (`xval()`/`rundown()`), not to `partition()`/`bsplit()` as exercised by the single, deterministic full-data fit.

#### 5.6 Binary-level instrumentation: locating exactly which folds diverge

To go beyond "cross-validation is somehow involved" and find precisely *where*, identical debug instrumentation was added to **both** copies of `xval.c` (temporarily — see §5.8 for reversion), immediately after the existing `rundown(xtree, j, cp, xpred, xtemp);` call inside the per-fold "run the extra data down the new tree" loop:

```c
rundown(xtree, j, cp, xpred, xtemp);
{
    int _dbg_k;
    fprintf(stderr, "XVALDBG xgroup=%d obs=%d xtemp=", xgroup, j);
    for (_dbg_k = 0; _dbg_k < rp.num_unique_cp; _dbg_k++)
        fprintf(stderr, "%.17g,", xtemp[_dbg_k]);
    fprintf(stderr, "\n");
}
```

Because `rpart/src/xval.c` is a read-only, permission-locked file (`-r--r--r--`) inside the reference R package tree, it could not be edited in place; instead the entire local `rpart/` source directory was copied to a scratch location, patched there, and installed into a scratch `.libPaths()` library via `R CMD INSTALL --no-multiarch --library=<scratch>/rlib <scratch>/rpart_dbg` — i.e. a debug-instrumented **local rebuild of R's actual, unmodified-except-for-this-print-statement `rpart` package**, loaded via `.libPaths(c("<scratch>/rlib", .libPaths()))` ahead of the CRAN-installed copy. The Python copy of `xval.c` was patched identically and the extension rebuilt via the normal `pip install --no-build-isolation .` flow.

Both instrumented builds were run against `fit1`'s exact configuration (`method="poisson"`, `usesurrogate=0`, `cp=0`, `xval=xgroup`) with `stderr` redirected to a file. Both produced exactly **146** `XVALDBG` lines (one per observation, once it falls into a held-out fold). `diff` between the two logs showed:

- **7 of 10 folds (`xgroup` values 0,1,2,4,5,7,8) match line-for-line, value-for-value, to all 17 significant digits printed**, for every one of the 9 cp columns.
- **3 folds diverge: `xgroup=3`, `xgroup=6`, `xgroup=9`** — and only ever starting from cp column index 6 onward (0-indexed) — i.e. exactly the deepest columns (`nsplit` 7, 8, 9) that the test file already flags as suspect. Columns 0–5 are identical even within these three "bad" folds.
- Representative diverging lines (fold `xgroup=3`): observation 43 gets R `xtemp[6..8] = 0.94231701405719814` (repeated 3×) vs. Python `1.433356506351513`; observation 83 gets R `1.3513041337898968` vs. Python `0.75977768637618492`; observations 133 and 143 both get R `0.81134826991913012` vs. Python `0.54149023573279376`. The same pattern recurs for `xgroup=6` (observations 46, 56, 116) and `xgroup=9` (observations 119, 129, 139).

This is the most direct evidence produced in either Phase 11 session or this addendum: **it is not "R and Python disagree on `xerror`"** in some diffuse, aggregate sense — it is that **13 specific (observation, fold) pairs, out of 1,460 total (146 obs × up to 10 folds), get a different per-observation prediction error from column 6 onward**, and every other one of the 1,447 pairs matches to 17 significant digits.

#### 5.7 Two distinct mechanisms identified within the 13 divergent cases

Cross-referencing the 13 divergent observation indices against `stagec.csv`'s missing-value pattern (`eet` missing at rows 23,106; `g2` missing at rows 1,7,56,110,114,130,143; `gleason` missing at rows 6,86,92 — all 0-indexed) separates the 13 cases into two groups with two different explanations:

**Mechanism A — a genuine, pre-existing latent bug in `rundown.c`, present verbatim in both R's and `r2py_rpart`'s (byte-identical) source, not a Python-port defect.** Observations 143 and 56 are among the divergent set and are *themselves* missing `g2` (the variable used repeatedly as a split at the depth in question — nodes 4/5/26/52 in the printed tree all split on `g2`). `rundown.c`'s `oops:` label is reached whenever `branch()` cannot route an observation further because its split variable is missing and `rp.usesurrogate < 2` (true here: `usesurrogate=0`) forbids falling back to a surrogate or default-majority direction:

```c
oops:;
    if (rp.usesurrogate < 2) {  /* must have hit a missing value */
        for (; i < rp.num_unique_cp; i++)
            xpred[i] = otree->response_est[0];
        xtemp[i] = (*rp_error) (rp.ydata[obs2], otree->response_est);
        return;
    }
```

The `for` loop correctly back-fills `xpred[i..num_unique_cp-1]`, but does **not** touch `xtemp[i..num_unique_cp-1]` inside that loop — it only ever writes a *single* `xtemp[i]` element, executed **after** the loop has already run `i` up to `rp.num_unique_cp` (one past the last valid index for the intended array). Recall from `xval.c` that `xtemp`, `xpred`, and `cp` are three views into one `CALLOC(3 * rp.num_unique_cp, ...)` block, laid out contiguously as `xtemp[0..n-1]`, `xpred[0..n-1]` (`= xtemp+n`), `cp[0..n-1]` (`= xpred+n`), where `n = rp.num_unique_cp`. So `xtemp[i]` with `i == rp.num_unique_cp` does not throw or corrupt memory — it silently aliases `xpred[0]`, **not** any of the intended `xtemp[i_original..n-1]` slots. Those slots are simply **never rewritten** by this call and retain whatever was left there by a *previous, unrelated* call to `rundown()` — because the whole `xtemp` block is allocated once per `xval()` invocation (outside both the per-fold and per-observation loops) and is never cleared between observations or between folds. This is a real defect in the *original, upstream* rpart C source (confirmed identical in both `rpart/src/rundown.c` and `r2py_rpart/src/rundown.c`), essentially never triggered in ordinary use because it requires the specific combination of `usesurrogate<2` *and* a held-out cross-validation observation missing its split variable at a depth reached only by a very lightly-pruned (here, `cp=0`) tree. It directly and fully explains why observations 56 and 143 — the only two of the 13 divergent cases that are themselves missing `g2` — get an incorrect, essentially arbitrary "stale" value carried over from whichever unrelated computation last touched that memory slot, and why that stale value differs between the R and Python processes (different allocation/call histories leave different leftover bit patterns in the reused buffer, despite both being deterministic and reproducible run-to-run *within* a given language/build).

**Mechanism B — a genuinely different deep tree per affected fold, not yet fully root-caused.** The remaining 11 divergent observations (43, 83, 133 for `xgroup=3`; 46, 116 for `xgroup=6`; 119, 129, 139 for `xgroup=9`; etc.) are **not** missing any predictor value themselves. Because `rundown()`'s main (non-`oops`) loop always freshly recomputes `xtemp[0..num_unique_cp-1]` from scratch for every call that does not hit `oops`, these observations' divergent values cannot be stale-buffer artifacts of Mechanism A — they are freshly, correctly computed by each language's own `rundown()`, and yet the two languages compute genuinely different numbers (e.g. obs 133: R gets `0.81134826991913012`, Python gets `0.54149023573279376`, both fully reproducible and internally self-consistent — obs 143, which is missing `g2`, coincidentally also lands on the *same* stale value as obs 133 within each language, i.e. `0.81134826991913012` in R and `0.54149023573279376` in Python, suggesting Mechanism A's stale carry-over happens to inherit Mechanism B's already-diverged value in this instance). Since the *same* `xtree` (built once per fold, before any `rundown()` calls) is shared by every observation in that fold, this proves that **the refit tree structure for folds 3, 6, and 9 itself differs between the R and Python binaries** at some very small, deep node — most plausibly because rpart's split-search (`bsplit.c`'s `(*rp_choose)(...)` call and its comparison `if (improve > (rp.iscale * 1e-10))` against competing candidates) encounters an exact or near-exact floating-point tie between two candidate splits at that node, and the deciding comparison resolves oppositely between the two binaries due to a sub-ULP evaluation-order difference somewhere upstream (e.g. inside `poisson.c`'s deviance/goodness formula for this method). This part of the investigation was **not** fully root-caused to one specific expression or line — doing so would require instrumenting `bsplit.c`/`choose_surg.c`/`poisson.c` to dump every candidate variable's `improve` value at the specific deep node for fold 3 and diff them, which is a further, feasible but not-yet-executed step for a future session. What *was* ruled out for Mechanism B specifically: raw data precision (§5.2), C source text (§5.3), and compiler/optimization/ISA flags (§5.4) — all identical, so the residual candidate cause is a genuine, sub-ULP floating-point non-reproducibility between the two compiled binaries in a numerically ill-conditioned (near-tied) split comparison, not a logic error in either port.

#### 5.8 A caveat surfaced in passing: `usesurrogate` materially changes tree size, not just cp-column count

While probing whether Mechanism B was specific to `usesurrogate=0`, `fit1` was re-fit with `control=rpart.control(cp=0, xval=xgroup)` (i.e. dropping the explicit `usesurrogate=0`, reverting to the default `usesurrogate=2`) in both R and Python. This produced a **new, larger point of difference not previously documented anywhere in Phase 11**: R's cptable grew to **10** rows (`nsplit` up to 10) while Python's cptable had only **9** rows (`nsplit` up to 9) — i.e. an actual difference in the *number of splits* in the fully-grown tree once default surrogate-based missing-value handling is exercised together with `cp=0`, not merely a cross-validation-statistic discrepancy. Rows 1–5 still matched exactly between the two 9-and-10-row tables, and row 6 already diverged in `xerror` even though it was still within the previously "matching" region for the `usesurrogate=0` variant. This is a **different configuration than anything `testall.R` actually exercises** (the real `fit1` in the R test script always passes `usesurrogate=0` explicitly), so it does not contradict or supersede any of the findings above, but it is flagged here as a new, separate, and apparently more severe latent discrepancy — in default (`usesurrogate=2`) surrogate-based missing-value handling under `cp=0` — worth a dedicated investigation in its own right in a future session. It was not pursued further in this addendum because it falls outside the scope of the already-committed `test_testall.py` assertions.

#### 5.9 Reversion and final state

Every artifact of this investigation was created under the session's scratchpad directory (never inside the repo) with two narrow exceptions, both reverted before concluding: (1) the temporary `-O2 -march=nocona -mtune=haswell` addition to `r2py_rpart/meson.build`'s `c_args` (§5.4), and (2) the temporary `XVALDBG` `fprintf` instrumentation added to `r2py_rpart/src/xval.c` (§5.6). Both were reverted via `git checkout -- r2py_rpart/meson.build r2py_rpart/src/xval.c`, confirmed clean via `git status --porcelain` on those two paths, and the extension was rebuilt via `pip install --no-build-isolation .` to restore the installed `r-to-python` environment to the pre-investigation state. `pytest tests/test_testall.py -q` (and, separately, the full suite) were re-confirmed passing (6/6 and 38/38 respectively) after reversion. No test assertions, fixtures, or library source files were changed as a result of this addendum — it is a pure diagnostic investigation, and the existing loose sanity-bound assertions in `test_testall.py` for the affected trailing cptable rows remain the correct, appropriately-hedged way to encode this known-and-now-substantially-better-understood (though not 100%-root-caused) discrepancy.

#### 5.10 Updated status of the open item

The "unresolved item" recorded at the end of §3 is updated as follows: the discrepancy is **conclusively confirmed to originate inside rpart's C cross-validation code** (not the Python port's data marshaling, formula parsing, or any of the seven bugs already fixed in §2.4 item 7), and is now understood to be **two compounding effects** rather than one: (A) a real, fixable-in-principle latent indexing bug in the shared `rundown.c`'s `oops:` fallback (affects only held-out observations that are themselves missing a deep split variable under `usesurrogate<2`), and (B) an unresolved, more fundamental floating-point tie-break sensitivity in the split-search comparison for very small, deep nodes in specific cross-validation folds, which affects both R and Python identically in kind (both are internally deterministic and reproducible) but not in which candidate split wins. Fixing Mechanism A in `r2py_rpart` would require deliberately *diverging* from R's C source (to fix a bug R itself still has), which is out of scope for a port whose goal is behavioral parity with R; fully explaining Mechanism B remains future work, with a concrete next step identified (§5.7) for whoever picks it up. The `usesurrogate=2`/`cp=0` tree-size discrepancy found in §5.8 is logged as a new, separate, not-yet-investigated item.
